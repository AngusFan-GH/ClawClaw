# GenUI result cards

English | [中文](genui.zh.md)

GenUI implements opt-in result cards with local chart, table and isolated HTML interactions. It does not replace the upstream Markdown renderer, observe the conversation DOM, or change layout ownership. The pinned upstream checkout is unchanged.

## Current scope

The product goal is to show useful charts and small interactive snippets directly in chat. Keep the standard components, isolated HTML, explicit reset, fullscreen, HTML download and text fallback. Source is retained with the conversation. Existing input restoration is a convenience, not a promise to resume every custom interaction. Custom-state hooks remain available for compatibility and are not a default generation requirement. State migrations, a storage-management UI, sharing, collaboration, additional export formats and additional component families are deferred until a concrete user need justifies them.

## Enable in a test Profile

GenUI is off by default. In **Settings → General**, turn on **Visual responses**. The switch saves to the active Profile and takes effect immediately, without restarting. Like the other switches, it animates immediately and locks while saving, without adding a saving message or changing the row layout. A failed save restores the confirmed value and shows an error. Read-only settings cannot be changed. Rendering follows confirmed Host state. Turn it off in the same place to restore text results.

For manual Profile configuration, add or edit this override in the active Profile's `cordis.patch.yml`, after inserted entries:

```yaml
- id: desktop-genui
  config:
    enabled: true
```

Restart the Host after manually editing the file. The existing settings transport can also update the entry's `enabled` field. Set it to `false` to remove both model tools, the prompt contribution and the custom result view. Saved tool results retain their ordinary text content. Profile preparation preserves explicit choices and adds the entry to older Profiles without enabling it.

Ask naturally for a visual comparison, plan or chart; the enabled feature guides the model to call `clawclaw_render_ui`. Naming the tool in the request is optional. `clawclaw_validate_ui` returns field diagnostics without displaying a card. The document argument is:

```json
{
  "format": "clawclaw.genui/v1",
  "title": "Service status",
  "items": [
    { "type": "stat", "label": "Healthy", "value": 3 },
    { "type": "table", "columns": ["Service", "Requests"], "rows": [["API", 20], ["Worker", 4]] },
    { "type": "progress", "label": "Review", "value": 50 }
  ]
}
```

Prefer the `document_json` tool parameter: serialize the complete document as one JSON string. The legacy `document` object remains accepted. Supply exactly one parameter. This keeps nested JSON arrays intact in model transports that otherwise emit `{item: ...}` wrappers. Malformed wrappers still fail strict validation; they are never silently repaired. Failed validation returns an explicit inline retry hint.

## Plugin boundary

The Host is the opt-in Cordis plugin `desktop-genui`, exported as `dsh-plugin-desktop/genui`. It owns tools, prompt, presentation guard and the scoped state API. The Client is the built-in Cordis child plugin `desktop-genui-client`; the desktop Client registers it with `ctx.plugin`, rather than directly installing its views. Its own lifetime owns rendering slots, settings row, locale registration, subscriptions and styles. Disposing the child releases those registrations. Disabling Visual responses removes interactive rendering, tools and visual styles, while retaining readable historical text and the settings row for re-enabling. This is modular code inside the desktop package, not a separately published or independently installable npm package. Electron's srcdoc navigation policy is a generic host-platform safety capability in `isolated-preview-navigation.ts`, not a dependency on GenUI business logic. The upstream checkout remains unchanged.

Generation notices reflect actual render/validate lifecycles. Validation alone never counts as a displayed result. Corrective local-browser denials become a friendly inline-preparation notice in the answer area; technical diagnostics remain in work details. Completed failures offer an explicit Retry display action through the owning session's standard conversation send API. Retry creates a visible follow-up, preserves the composer draft and cannot silently send into another session. Successful results replace progress, and unknown historical turn state never shows an endless spinner.

## Protocol and ownership

Supported types are `text`, `card`, `row`, `stat`, `table`, `progress`, `callout`, `steps`, `chart` and `html`. Standard component text is literal; no HTML, arbitrary styles, executable expressions or model actions are interpreted outside isolated HTML previews. Tables sort locally and use semantic table headers with sort state. Limits are 64 KiB of serialized JSON, 200 components, eight component levels, 50 table rows, 12 columns, 24 steps, 2,000 characters per text field and 160 per title or label. Invalid or oversized documents produce diagnostics instead of silently discarding data. No repair is attempted.

The Host validates the document, parses HTML and compiles inline JavaScript without executing it to reject syntax errors and unclosed scripts, then uses the tool output contract to project it into replayable `meta`, while preserving a readable text result. The Client validates that metadata again. It renders settled results only; preparing/running arguments never become interactive UI. Successful results appear in the public answer, outside collapsed work details. Results without an explicit placement reference remain in order at the answer's end. An optional nonblank `resultId` (at most 160 characters) replaces the result with the same ID in that Turn, preserving its original position. An unnamed HTML result replaces the previous unnamed HTML result in the same Turn; use distinct IDs for independent interactive examples. Other unnamed results remain independent. Failed or invalid updates cannot replace a valid card; unrecognized metadata retains its saved text separately. This reads the owning Session's Turn-scoped Chat projection, including nested PTC results and hidden process nodes; it restores from history without another model call. Work details keep a compact text record and do not start another interactive instance. If every visual result fails and the Turn has no public answer, the latest saved prose explanation is recovered outside the collapsed process; reasoning is never promoted. Missing, invalid or future metadata falls back to saved text. Session and call identity come from the owning view. Local sorting is ephemeral and does not write shared state or send model messages.

For placement between paragraphs, render a document with `resultId: "pi-demo"`, then put `[[clawclaw-ui:pi-demo]]` alone on a line in the final answer. The Client shows that result at the reference, once, without a duplicate at the tail. Use the same ID when correcting a result. Prose segments keep the native Markdown renderer, including math and code. Literal references in code remain literal. Streaming and process commentary do not mount interactive results. Reference-link or footnote definitions retain one Markdown pass and fall back to end placement. Historical answers without references retain their layout. Copy replaces placement references with the saved readable result text.

The Client uses the desktop's shared `registerEntryProjection` adapter for `assistant-step` and `turn-tail`, preserving native locale, injected hooks and child-slot ownership without replacing the original components in place. The adapter remains installed in text-only mode so disabling Visual responses replaces historical placement references with readable saved text, without mounting iframes or requesting presentation state. Full plugin disposal removes the projections without releasing native child declarations. Real SlotCore tests cover late registration, native owner reload, repeated cleanup and text fallback. This remains an adapter for the pinned registry, not a new upstream decorator API.

The feature follows confirmed Host configuration and disposes its tools, prompt, slot and styles. Result source stays in Session metadata; a separate bounded Profile storage domain holds HTML presentation state, without adding it to model context. Action delivery, business drafts, additional export formats, inline fences and sidechat integration are outside the current product scope.

## Charts and presentation

Charts use Apache ECharts with SVG rendering. The `chart` node accepts `kind` (`bar`, `line` or `pie`), a `title`, `categories`, `series` (each with a unique `name` and `values`) and an optional `unit`. For example:

```json
{ "type": "chart", "kind": "bar", "title": "Service requests", "categories": ["API", "Worker", "Cache"], "series": [{ "name": "Requests", "values": [20, 4, 100] }], "unit": "requests" }
```

A document allows eight charts, each with at most 60 categories and four series. Pie charts allow 12 categories and one nonnegative series. Values must be finite and have magnitude at most 10^15. Bar and line charts accept `null` for missing values; zero remains zero. Series lengths must match categories. Arbitrary ECharts options, code and HTML are rejected.

Legend toggles only affect the current local view. Pie legends show values and shares of the currently visible categories, with an explicit scope explanation after filtering and a Restore all action. Their data tables always retain all categories and shares of the original total. Single-series bar/line charts show a series label without an unnecessary toggle. Every chart includes an expandable semantic data table; empty, all-hidden, all-missing and zero-sum pie data each explain the specific reason. Hidden data can be restored with one action. Rendering failures automatically expand the data table. Charts resize with the container and follow light/dark themes. Long-name or more-than-eight-category bars use a horizontally oriented comparison with vertical scrolling. Trends with more than 12 categories scroll horizontally, preserving all points and their source order. Plot heights follow content, with bounded scroll viewports. Keyboard users can scroll the plot region and expand the exact data table. Unmounting disposes charts and observers. Cards use theme colors, grouped metrics, restrained borders, numeric table alignment and compact progress bars. Callouts distinguish info, success, warning and error with labels, icons and semantic accent colors. The model is instructed to provide concise conclusions without repeating card data. The General setting uses a concise description without example requests.

## Local interactive HTML

HTML interactions and explicit structured cards render as independent sibling surfaces in the chat answer, before its message action buttons. A mixed document does not acquire one enclosing visual card. Narrative text and text-only card groups flow without a card shell; their headings remain, and split continuations retain a contextual heading. Adjacent ordinary data components can share a surface; an explicit row of ordinary cards can remain side by side. Historical HTML nested inside card/row containers is lifted out without changing content order or its original saved state address; source metadata is unchanged. Each HTML fragment has its own title and toolbar, without a duplicate document heading. Separate documents and resultIds allow independent placement between prose paragraphs. Opening tool details or another page is unnecessary.

Use `html {type:"html",title:string,html:string,fallback:string}` for small self-contained calculators, filters or simulations that standard components cannot express. Each document allows two fragments, each at most 32 KiB of UTF-8 source. Title, source and a readable fallback are required. Tool text contains the fallback, not executable source; source remains in durable metadata for replay.

The Client runs fragments in an opaque-origin `iframe` with only `allow-scripts`. The initial policy blocks external resources, connections, nested frames, workers, objects, base URLs and form submission. Inline CSS and JavaScript are supported; external libraries, imports and eval are unavailable. Electron additionally cancels navigation initiated by or targeting a srcdoc frame, because CSP alone does not block self-navigation. Ordinary plugin iframe navigation remains unchanged. No Electron, filesystem, session, tool or privileged action bridge is exposed. This is a presentation runtime, not a general application or security boundary for arbitrary hostile workloads; CPU and memory quotas are not provided.

A narrow source-checked message channel reports readiness, failure, bounded height (120–720 px) and preferred inline width (320–960 px, still constrained by the chat column); it accepts no action commands. Small form tools start with a 640 px maximum. The runtime follows authored content width caps; responsive visuals without a cap retain the available column width. Toolbar, notices and content share that width. Fullscreen removes the inline width cap and restores it on exit without recreating the iframe. A separate bounded JSON message carries only presentation state. Theme updates go into the frame without resetting its local inputs. A button error after readiness keeps the remaining content visible. Failed startup or interaction offers an explicit Regenerate action through the owning Session prompt API; no request is sent automatically. Syntax validation cannot prove that every button handler exists or that the simulation is mathematically correct. Actions distinguish Retry save, Retry reset, Reload saved inputs, Reload content, and Request regeneration. Only regeneration asks the model for a follow-up answer, with explicit sending/sent/failure feedback and a note to look in that answer; it does not claim the current card was repaired. Saving retries retain the live iframe; reloading reruns the existing source with saved inputs. The outer toolbar has only Fullscreen and Download HTML. Fullscreen keeps the same iframe instance and inputs; leaving fullscreen restores the inline height. Download creates a self-contained HTML file with the latest bounded presentation snapshot and no connection to Host APIs. Automatic native-control restoration and explicitly saved custom state work in that file, but arbitrary JavaScript heap state is not captured. Animation controls belong inside the snippet. Restore initial values is a secondary action inside the collapsed description and explicitly clears saved inputs. Loading reserves the content height. Save failures offer Retry without reloading the snippet. Views without a Regenerate callback can Reload with current inputs after a runtime error. Errors or an eight-second startup timeout expose the description. Read/save failures are visible and failed loads do not overwrite stored data. Native input, checkbox, radio, select and textarea values automatically persist in the current Profile and restore on refresh, history reopen or Host restart. Password, file, hidden, `data-private` and `autocomplete="off"` fields are excluded. Saved controls are restored and emit input/change events so computed outputs update. Custom state uses `window.clawclaw.getState()` and `window.clawclaw.setState(json)`. This is not arbitrary JavaScript heap persistence; scripts must opt in for custom state. State is limited to 100 controls, bounded JSON, and 16 KiB per fragment. A Profile holds at most 1,000 snapshots; reaching the limit reports a save failure and never silently evicts existing entries. Do not put secrets into snippets or imitate permission dialogs. Static charts should continue to use the standard chart component.

Example request: “Create a local price calculator with unit price and quantity inputs, a live total and a reset button. Include a text explanation.” Users do not need to name a tool. Small visual and HTML requests default to direct chat rendering. The model is instructed not to create a file, start a server, open a browser or run browser automation just to display or verify an inline result. Explicit website, standalone-file, export or browser requests retain their requested workflow; researching source data remains available. When the latest human request explicitly asks for an inline result, an enabled Host execution guard denies local file/loopback navigation through browser_navigate before the browser body runs. Explicit browser instructions and external research URLs remain allowed. This is a narrow presentation rule, not a general browser sandbox. Validation success explicitly instructs the model to call render; validation itself still displays nothing.

The architecture follows the general isolated-document approach, informed by the locally available visualization preview wrapper and [OpenAI’s visualization overview](https://learn.chatgpt.com/docs/visualizations). The ClawClaw runtime and styles are original; this does not claim to reproduce Codex’s private app internals.

## Desktop acceptance

Automated and browser checks do not replace one real Desktop acceptance run. In the running app, enable Visual responses and ask for a price calculator in chat. Check inline interaction, placement between prose, fullscreen without state loss, downloaded HTML, disabling/re-enabling with readable text and restored inputs, refresh or conversation reopen, explicit reset and reopening historical source. For charts, check legend filtering and the source data table. Record real failures and fix them before expanding the feature. This checklist is pending until performed against the running Desktop app; it does not launch the graphical app automatically.

## Verification and provenance

Run the focused GenUI suites, typecheck, build and the standard headless gate. Tests exercise the real DSH tool registry, serialize and restore a Session result, check profile upgrade/enablement, render components in jsdom, and exercise the real ECharts SVG renderer without a browser or GPU. They do not establish painted Electron layout or live model behavior; graphical application launch remains explicit.

This increment is an original implementation informed by [dsh-genui](https://github.com/omdsh-dev/dsh-genui), particularly its separation of validation, tool metadata and presentation. It copies no source files and adds no dependency on that package. Future source migration must pin its origin and retain applicable license notices and regression tests.
